# `@nts/sdk` — design

**Status:** draft 1, interface only. No implementation. Node.js APIs are out
of scope for now (they stay a separate layer in `runtime/node`, usable beside
this package on desktop targets).

## 1. Principle: standards first, SDK for the gaps

A capability is served by the first layer that actually covers it:

| Situation | Decision |
|---|---|
| A Web API fully solves it | Use the global directly (`navigator.mediaDevices.getUserMedia`, `fetch`, `new Notification(...)`). No SDK wrapper. |
| A standard covers part of it | SDK adds only the missing part, accepting/returning the standard objects (continuous barcode scanning over a standard `MediaStream`). |
| A common multi-step workflow | SDK may add one high-level verb/component (`camera.capturePhoto()`, app key/value storage). |
| No standard exists | SDK defines an original portable contract (`windows`, `tasks`, secure storage). |
| Unique to one OS | Generated native projection. SDK wraps only if a portable intention exists. |

Global Web types for native targets live in [`lib.native-dom.d.ts`](lib.native-dom.d.ts):
the application subset of TypeScript's `lib.dom.d.ts` copied verbatim
(no `Window`/`Document` tree) plus MDN-sourced additions for APIs lib.dom
lacks yet (`BarcodeDetector`, Generic Sensors, Contact Picker, Battery).
It is generated by `tools/extract-native-dom.py` — temporary until nts
generates a native lib from WebIDL. Presence in the lib is a typing
convenience, **not** a claim a target implements it (see `availability()`).

## 2. The re-export convention

Every SDK module names its standard part explicitly, by re-exporting the
global types it complements:

```ts
/** Re-exported so `@nts/sdk/clipboard` is self-describing in the API reference. */
export type Clipboard = globalThis.Clipboard;
export type ClipboardItem = globalThis.ClipboardItem;
```

This makes one documentation page per capability possible (standard verbs,
SDK gaps, native escape hatches) without a proprietary twin of anything.
Type re-exports only: standard *values* are the globals (`navigator.clipboard`,
`new Accelerometer(...)`), never re-exported constants.

Modules whose capability is fully standard (`clipboard`, `share`, `sensors`
via the Generic Sensor globals) consist of re-exports and documentation
alone — an honest, discoverable "there is nothing to add here".

## 3. Conventions for the parts that are ours

1. **Standard objects cross every boundary**: `Blob`, `File`, `MediaStream`,
   `FileSystemFileHandle`, `URL`, `AbortSignal`, `EventTarget`. SDK types
   are plain data; an SDK handle exists only where identity/lifetime/
   permission state is real (`DocumentHandle`, `MediaAsset`).
2. **Async + `AbortSignal`** on every operation. Sync only for facts known
   at startup (`platform`, `app.info`).
3. **Availability ≠ permission ≠ failure.** `availability()` never throws
   and never prompts; `permissions` is the Web Permissions API plus the two
   mobile facts it lacks (`limited`, `canAskAgain`); operations reject with
   a coded `AppError` (core), using the `DOMException` name where the Web
   has one.
4. **User dismissal is a value**: single-item pickers resolve `null`,
   multi-item pickers resolve `[]`. `AbortSignal` aborts still reject.
5. **Events are `EventTarget` events** (typed); value streams are
   `AsyncIterable`/`Watch<T>` and are `AsyncDisposable`. Resources are
   objects you `await using`, not singleton state.
6. **No fake portability**: `PushToken` names APNs/FCM/Web Push;
   `approximate` location is labelled; unsupported is reported, never
   silently weakened (no plaintext "secure" storage in a browser).
7. **No implicit permission prompts** except inside system UI that carries
   its own (pickers), which therefore need no permission.

## 4. Module map (draft 1)

Source layout mirrors capability, imports do not: `src/shared/` holds
what can be implemented honestly on both phone-class and desktop
targets with the same contract, `src/mobile/` only what requires a
phone-class device (today: haptics, pedometer, barometer), and
`src/desktop/` only what requires a windowed desktop OS (windows,
shell, displays, capture sources). Per-target truth (browser and
Chromium included) is `availability()` today and a support manifest
later; public imports stay flat (`@nts/sdk/camera`) so a module can
change group without breaking code. Mixed modules get split, as
`screen-protection` (out of capture) and `brightness` (out of device)
were when this rule was adopted.


| Module | Standard part (re-exported) | SDK gap part |
|---|---|---|
| `core`, `app`, `permissions` | — | platform facts, lifecycle, permission request/limited |
| `clipboard` | Async Clipboard (+ ClipboardItem, clipboardchange) | no-prompt type peek, sensitive writes (see operations.md) |
| `share` | Web Share | — (fully standard) |
| `camera` | `getUserMedia`, `ImageCapture`, `MediaRecorder`, `BarcodeDetector` | continuous scanner over a `MediaStream`; system camera workflow |
| `photos` | `File`/`Blob` | system picker, library save/albums |
| `documents` | File System handles, OPFS via `navigator.storage` | user document grants, known folders, save/open workflows |
| `storage` | — | app key/value settings |
| `security` | WebAuthn (`navigator.credentials`), Web Crypto | secure secret storage, biometric authentication |
| `location` | Geolocation | background tracking service, geofencing |
| `notifications` | `Notification`, Web Push, app badging | local scheduling, native push tokens, tap responses |
| `tasks` | — | OS-managed background work, named handlers |
| `contacts` | Contact Picker | address-book query/create/update/delete |
| `calendar` | — | calendars, events, reminders |
| `device` | Generic Sensors, Battery, Wake Lock, Vibration | haptics patterns, pedometer |
| `linking` | — | open URLs out (inbound links are `app` events) |
| `windows`, `shell` | — | desktop windows; menus, tray, shortcuts, autostart, dialogs |
| `auth`, `images`, `media`, `network`, `compose`, `printing`, `store`, `appearance` | WebAuthn, ImageBitmap/WebCodecs, Web Audio/MediaSession, Network Information | added by the Expo coverage pass (`docs/coverage.md`) |
| `displays`, `power`, `capture` | Wake Lock, `getDisplayMedia` | added by the desktop pass (`docs/desktop-ledger.md`) |
| `ui` (components) | React DOM host semantics | portable component types; design in `docs/ui/components.md`, platform truth in `docs/ui/platform-inventory.md` |

Deferred/deleted vs draft 0: proprietary camera sessions, portable
`location.current/watch` (Geolocation does it), `files` directory objects
(OPFS/Node/documents split the job), `sdk.fetch`-anything. UI components
(`CameraView`, `MapView`) belong to the React layer over these types.

## 5. How implementations will attach (later)

Public interface here; internal *provider* interfaces per platform lane
(the `runtime/web-platform` provider pattern). One provider can back both
a global and an SDK verb (one capture stack under `getUserMedia` and the
scanner). Apps never select providers.

## 6. Open questions

1. **Lib ownership**: who owns generating `lib.native-dom` from WebIDL, and
   does the Blink host share it? (Extractor is a stopgap; say so in the lib.)
2. **Target-narrowed typings** via export conditions vs `availability()` —
   compiler lane's call.
3. **Experimental standards**: which draft APIs in the lib do we bless with
   presence on native targets (Shape Detection, Contact Picker are
   Chromium-only on the web)? Adopting a well-defined draft natively is
   allowed here, but each needs a conformance claim per target.
4. **`share` dismissal**: we recommend `navigator.share` (rejects
   `AbortError` on dismissal, its specified behavior) — now consistent by
   construction since we don't wrap it. Confirm no SDK verb is wanted.
5. **Background execution envelope**: `tasks` handlers run headless; what
   globals exist there (no UI, which SDK modules)? Defines geofencing and
   background location delivery.
6. **`Date` vs Temporal** for schedules/calendars once the Temporal track
   lands (`docs/temporal.md`).
