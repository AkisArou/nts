# Landing gate tooling survey

**Status:** Draft. **Survey date:** 2026-11-05. **Scope:** the Linux landing gate in `AkisArou/nts` at `main`. This is a decision record, not a proposal to change gate code.

## 1. Recommendation

**Keep the proposed file-read recorder. Do not replace the gate with a build system or a test-selection service.** Run the existing 52 commands under a fail-closed Linux file-system recorder. Select a check by comparing its last *complete passing* input manifest with the replayed landing train, and share passing manifests in one content-addressed store across worktrees. A content-addressed store indexes records by hashes of their contents. Record successful reads, directory listings, failed existence probes, script and executable identities, relevant environment, toolchain versions, and data reached through symlinks. Treat any unobserved path, incomplete trace, new check, changed invocation, missing external input, or unverified toolchain as a cache miss. Never cache a time-sensitive, memory-sensitive, flaky, or otherwise nondeterministic verdict. Retain the nine cheap tree checks as unconditional work, the existing resource-aware runner, the train's base-and-tip safety rules, and the nightly full run. This is an **inference and recommendation**, not a proven guarantee: a read recorder is sound only within the file-system and ambient-state boundary it actually monitors. Tup proves the value of observed reads but requires an output-oriented build graph. BuildXL can trace and cache observed reads at industrial scale but requires a pip graph and sandbox integration. Neither is a drop-in replacement for this gate. [R1–R6, T1–T5, T6–T8]

## 2. Comparison

### The problem to preserve

The [step table][R1] describes 52 named checks. Nine have `treeOnly: true`. The existing [selector][R2] uses handwritten rules, Cargo metadata, TypeScript configurations, corpus membership, and script-reference discovery. It falls back to a broad gate for unknown paths. Its [range adapter][R3] evaluates both endpoint trees and unions their demands, so a changed selector cannot weaken an existing obligation. The [lander][R4] replays up to six compatible submissions on `main`, runs their joint gate, checks the summary, and isolates failures by halving a bad train. The [workflow][R5] also specifies special handling for held measurements, baseline failures, external inputs, and documentation. [External corpus inputs][R6] are symlinked from a shared checkout. They are not in Git.

The stated 30-minute landing run, 100-minute full run, 24 slots, 32 hardware threads, 32 GB of RAM, 900 GB of disk, and 20-crate count are **operating assumptions from the survey brief**. The listed files establish the machinery, not a fresh benchmark or hardware inventory. No speedup figure below is presented as measured.

**Terms.** An *owed check* is one whose verdict might differ for a candidate tree. A *declared input* is a file explicitly named in build configuration. An *observed input* is a file opened or inspected when a command ran. An *inferred dependency* comes from project metadata or a dependency graph. A *sandbox* restricts what a command can access. *Hermetic* means the command's result depends only on its specified inputs and controlled execution environment. A *cache key* is the fingerprint used to reuse an earlier result. A *remote cache* is storage accessed through a service; it does not imply remote execution. A *train* is a group of queued commits replayed onto `main` and gated together. A *person-week* (pw) is one engineer working for one week. **Every adoption and maintenance estimate below is an inference, not a vendor quote or a timed migration.** Maintenance is engineer-days per quarter (d/q). No tool here supplies the nts train, its split-on-failure behavior, or its measurement policy by itself.

**Reading the costs.** The pw estimates include a proof period with deliberate fault injection and nightly full-gate comparisons. They exclude a remote build cluster, because nts has none. The d/q estimates cover tool updates, rule/trace regressions, and cache repairs. A "wrap in a day" demo is not a safe migration. No claimed cache hit rate or speedup was measured.

**Cross-cutting findings.** Declared-input systems are good at cache reuse *after their build graphs are correct*. They are not an automatic repair for a missing dependency. A single opaque `cargo test --workspace` action is cheap to wrap, but usually invalidates on much of the workspace and misses read-only data outside the action input set. Splitting Rust into fine-grained rules costs much more. In contrast, a recorder can work at the existing check granularity, but cannot find an input that was not observable through its mount or trace. An observed-read cache is therefore conditional evidence, not proof of semantic purity. External tools, environment variables, directory existence, nondeterministic results, writes, and generated binaries all need explicit safety treatment. [R1, R2, R6, B1, T3, T6, M1]

**Recent exception: Nx.** Nx Cloud Ultracache is closer to the proposed design than older Nx comparisons suggest. Its [2026 documentation][M1] says it records actual reads on Workers, including inputs across project boundaries. However, no Worker recording occurs from this repository's local landing process. It can consume earlier recordings in some configurations, but cannot create them there. Bringing up CI and Workers solely for read tracing violates the present constraints and still leaves the gate scheduler, external SDKs and measurement policy to integrate. This finding depends on the **2026-11-05** documentation, not pre-2026 Nx assumptions.

## 3. The top two candidates, in detail

These are the two **existing tools closest to the observed-read requirement**. They are migration sketches for comparison, not alternative recommendations. Their cost estimates are inferences.

### A. BuildXL: strongest complete product, highest integration cost

**Fit.** BuildXL combines a declared process graph with runtime file-access observations. Its cache first finds candidates with a *weak fingerprint* of static inputs. It then checks a *strong fingerprint* derived from recorded dynamic inputs. The [cache design][T3] explicitly describes this. It also handles failed presence probes and directory membership [T4]. Microsoft documents use at 150,000-plus internal builds per day [T1]. This is real industrial evidence. But it has no native knowledge of nts's 52 step names, Cargo target sharing policy, frontend token pool, train ledger, or failure-halving semantics [R1, R4, R5].

**Migration sketch.**

1. **Start with read-only, low-risk checks:** `licenses`, `records`, `primitives`, `config`, then `format` and `rustfmt`. Run them as single BuildXL process pips. Compare their accesses with the current gate. Do not turn cache hits into landing passes yet. Keep the nine tree checks unconditional.
2. **Add an isolated tool check:** `tooling` or another test that writes only to a controlled temporary directory. Declare its complete outputs and process tree. Prove that a newly added script, a Git-ignored expected result, an absent file becoming present, and an external tool update each invalidate it.
3. **Model the release binary once.** Keep Cargo as the driver at first. Treat its build as one coarse pip with a private target directory and a declared binary output; never let two worktrees share a mutable Cargo `target`. Only then introduce observed-read pips for `outcomes`, `expect-ir`, `examples`, `llvm` and `jvm`. Make compiler binary hash and backend toolchains part of each verdict key.
4. **Import corpus and SDK identities.** Mount or enumerate the exact shared third-party inputs. Include Corretto, `d8`, clang, LLVM, Node/pnpm, Python, compiler flags and the canonical gate environment. Prove that an input symlink pointing outside the repo is covered. Model directory membership as well as files. The documented Linux sandbox has libc interposition and an eBPF rollout. Verify the actual kernel and privileges; the named files do not state them. [T2, T4, T5, R6]
5. **Only after equivalence**, let BuildXL return a cache-backed passing verdict to `land.ts`. Keep `run.mjs` as the CPU/memory scheduler unless BuildXL is shown to honor its slot and frontend budgets. Do not cache time/memory measurements or the hold/baseline result. Do not move the train queue into BuildXL.

**Selector and lander changes.** The rule-selection engine in `owed.mjs` would be retired **only after** every check has a proven BuildXL action. In `owed-range.ts` retain the base/candidate selector policy during migration. Replace `owedSteps` / `selectRange` in `land.ts` with a BuildXL request for all named pips at the exact replayed tip. BuildXL would return either “valid passing proof” or “must run” for each. The existing code would still union scope, enforce the nine tree checks, run uncached verdicts, validate summaries, gate the train and halve failures. Preserve `NTS_INTEROP_PROJECTS` and the doctest crate subset until their graph granularity is reproduced; silently widening them is safe but costly. **Delete** most path-to-check arms and derived `stepInputs` from `owed.mjs` only after the shadow comparison has found no under-selection. **Do not delete** `run.mjs`, `all.sh`, environment preflight, baseline checks, train journal or the failure isolation code. [R1–R5]

**Estimate:** **10–18 person-weeks**, plus **3–6 engineer-days each quarter**. About 2–3 weeks cover an executable BuildXL/Linux/sandbox prototype; 4–7 weeks cover process graphs, Cargo outputs and toolchains; 2–4 weeks cover the corpora and cache identity; and 2–4 weeks cover queue integration, fault injection and parity checks. Ranges overlap; these are planning estimates, not sums of independently priced work.

**Failure risks.** A BuildXL pip can inherit an undeclared host read if its sandbox does not observe it. The [Linux documentation][T2] says libc interposition misses static binaries and direct syscalls. The [flags][T5] describe eBPF as enabled by default and ptrace fallback for static programs, with cost. Its [file-system modes][T4] document an enumeration-versus-performance trade-off and a known possible nondeterminism. The 32 GB machine may also pay for extra materialization and process bookkeeping. Remote cache capacity brings no immediate advantage without a second machine. These risks demand measured experiments, not an assumption that Microsoft scale makes nts integration safe.

### B. tup: best read-tracing antecedent, poor output fit

**Fit.** Tup observes file reads during a command and uses them as invalidation edges. A Tupfile still declares each command and the outputs it creates. Tup requires generated outputs to be in the directory of the corresponding Tupfile, and monitors generated-file ordering. It is not just a read-recorder executable. The [manual][T6] says external files are outside the tracked hierarchy by default. Setting `updater.full_deps=1` needs Linux user namespaces or elevated setup and does not currently work with some external writers. There is no documented, cross-worktree cache of “this standalone check passed at these Git blob IDs” that could be adopted unchanged.

**Migration sketch.**

1. **Try the tree-only checks first.** Give `records`, `licenses`, `config` and `primitives` one Tupfile rule apiece, each with a declared temporary or stamp output. Retain unconditional execution for the nine cheap checks so a stale stamp cannot pass a landing. Compare Tup's read graph with a separately collected trace. Test a new `nts.config.ts` and removal of a referenced file.
2. **Add an isolated check with stable outputs.** `tooling` is a candidate only after its Android and JVM host dependencies are explicit. Keep all outputs under a dedicated build directory. Let Tup detect accidental reads of another rule's generated output.
3. **Probe Cargo before migrating it.** Running `cargo build --release` or `cargo test --workspace` as a Tup command means Cargo can write many objects, lockfiles and intermediates in `target`. Tup's rules require known outputs and reject undeclared writes. Either put Cargo in a separate controlled directory and treat its results as opaque, or replace its graph. Both depart from an unchanged wrapper. Stop if the probe cannot avoid false failures or silent exclusions.
4. **Test external roots.** `inputs.sh` links TypeScript, test262, Node material and other corpora into the gate worktree. Prove that Tup tracks their resolved external files under `full_deps`, including additions to enumerated directories. Do not just ignore `third_party` or the toolchain closure to make the build green.
5. **Test one native differential check** (`examples` or `llvm`), its expected files in `results/`, its compiler binary and its toolchain. Disable Tup incrementality for metric-bearing checks. Do not turn a Tup “nothing to do” into a pass until all dependencies and output checks have passed shadow validation.

**Selector and lander changes.** Replace the `owed.mjs` path-rule decision with Tup's database-derived dirty commands, but only for enrolled checks. The unresolved checks must still be selected conservatively by the old path rules or run unconditionally. In `land.ts`, ask Tup about the frozen train tip and union the dirty commands with its enforced checks. Keep the train construction, source-baseline check, split algorithm, holds and git-note proof. Keep `run.mjs` for token budgets and verdict completeness. **Delete** individual `owed.mjs` rules only as corresponding Tup-backed checks pass fault-injection tests. Once fully migrated, the old hand-maintained rule tables can go; however, Tupfiles, output declarations and their maintenance take their place. Its per-tree database must be protected against worktree mixing. [R1–R6, T6, T7]

**Estimate:** **6–11 person-weeks**, plus **2–4 engineer-days each quarter**. The first 1–2 weeks cover Tupfiles and tree checks. Another 2–4 address Cargo/generated outputs. Another 1–2 address external inputs, tooling and symlinks. Another 2–3 cover train integration, failure injection and trace-parity tests. Extra work is likely if Tup's restrictions force reworking test output paths.

**Failure risks.** Treating a passing stamp as stable can conceal a changed input if tracing omitted it. `full_deps` is not the default; its [documented limitations][T6] affect exactly this repo's installed SDKs and shared corpus checkouts. Excluding external generated paths can silence valid dependencies. Reusing a Tup database across branches is not the same as a content-addressed pass cache. tup is an excellent precedent for observing reads, but its build/output contract is not a cheap way to retain this gate intact.

### Soundness contract for the recommended recorder

The following is the **proposed acceptance test**, not a claim that the described FUSE recorder already implements it:

- **Discovery.** Observe the full descendant process tree, reads through `mmap` and symlinks, executable/interpreter loads, metadata/stat probes, directory enumeration, and failed file lookups. A new file must invalidate a previous directory listing. Relative and absolute paths must resolve to identities independent of a worktree pathname. Files on the host beyond the recorder's coverage must trigger conservative invalidation or an explicit complete toolchain fingerprint. A FUSE mount alone cannot automatically see every absolute host path.
- **Fingerprint.** For a tracked input use its Git blob ID **only after checking the executed checkout's bytes correspond to that object**. For Git-ignored corpora and generated inputs use content hashes. Include the exact check identity, command arguments, selected environment, result schema, baseline data in `results/`, compiler binary, Rust/clang/LLVM/JDK/`d8`/Node/Python identities, and relevant directory-membership digests. A changed check definition or newly discovered check has no old proof.
- **Pass store.** Write a passing result only after a complete trace and validated PASS summary. Use atomic publication to a single local shared cache. A cache hit must revalidate every recorded fingerprint. Missing data, an unreadable record, partial trace, corrupt entry, failed hash, inconsistent scope, or unresolved path means **run**. Never accept a cached FAIL/SKIPPED/NOT RUN result as a pass. A cache entry must not be allowed to turn off a gate step's required baseline or hold handling. The store is not trusted merely because the machine is local.
- **Policy.** Run the nine cheap tree checks unconditionally. Keep a **conservative explicit non-cacheable verdict policy** for ambient time, memory, noisy or nondeterministic checks, rather than a hand-maintained list of file inputs. A failed/incomplete recording is owed. If a check has no trustworthy prior complete recording, it is owed. Keep the nightly full check as an audit, not as permission to skip an uncertain landing check.
- **Train.** Compare the recorded dependencies against the exact **replayed base-to-tip** tree. For each check, use previous successful evidence only when every input and invocation still match. Union obligations from every member and from changes to check definitions; do not let the candidate version delete a base obligation. Preserve the existing `interop` project and doctest-crate selection until recorded at the same resolution. A train failure must still be attributable by the existing split algorithm. Keep the gate's CPU/memory admission and 24-slot resource policy outside the caching decision.
- **Proof of coverage.** Before enabling skips, inject changes into Rust and C sources, LLVM and JVM outputs, node addon inputs, `results/` expectations, a new corpus file, a removed file, a formerly missing file, a symlink target, script imports, a `pnpm` lockfile, an installed compiler binary and SDK paths. Verify each causes the right check to run. Compare with unoptimized full runs across multiple train compositions. Inspect trace loss and false skips, not just cache-hit rates. An occasional full-gate discrepancy blocks rollout.

**Recorder delivery estimate [inferred]: 3–7 person-weeks**, including tracing boundary proof, directories/negative probes, shared manifest storage and train integration; **2–4 engineer-days per quarter** to maintain it. This is less work than migrating the build, but not zero-cost. Actual effort may exceed it if FUSE cannot observe required host accesses; in that case use fail-closed broad execution until the observation boundary is repaired. This estimate is not derived from repository history.
