## Why so much was missed

- **Scoped audits.** Thirteen audits checked what was built, and each prompt listed its areas. Nothing asked "what does the design say about each construct?", so `as`, covariant arrays, typed arrays, `switch` and non-numbers were never examined.
- **No decision record.** DESIGN v1 had a "Decisions" section, and I removed it at v2. After that, a rewrite could drop a decision unnoticed, and three did: `Int32(x)`/`Int32.is` (v2), `.wrap`/`.clamp` (an approved plan, then v15), and `clamp`'s rounding. `DECISIONS.md` now restores the record. Every rewrite gets diffed against it.
- **One reference model.** I designed against C. The JVM, wasm, Kotlin, Apple and Win32 facts were never checked, and some are wrong in our files.

## D. Wrong in our files (to fix, no decision needed)

- DESIGN: "`Readonly<Int32>` is a plain number" (it is an object type).
- DESIGN: "never a false claim, except one" (A1–A8).
- DESIGN and `scalars.d.ts`: the float slot sentences contradict each other (C3).
- DESIGN: `Float128` is "`_Float128`", and `long double` "a double elsewhere": wrong for Windows x64 under nts's gnu toolchain, wasm and Android x86_64.
- DESIGN: `__Int8` "is the key nts's compiler reads". It isn't, yet.
- `scalars.d.ts`: "complete: every C type whose width is the target's" (C10).
- `scalars.d.ts`/Backends: the JVM Float16 path `Float.float16ToFloat` needs Android API 36. The Float16 row also says "arithmetic in f32", contradicting "JavaScript computes in doubles".
- `c/libdemo.d.ts`: `towupper` takes a `wint_t`, not a `wchar_t` (`WEOF` is 0xffffffff on glibc).
- `wasm/sqlite.d.ts`: an `i32` arrives signed through the JS API; a pointer at or above 2^31 needs `>>> 0`.
- `jvm/android.d.ts`: the Kotlin `Murmur3` binding (A9). The tour's "overloads pick as Java does" holds only for literals and scalars (A4).
- `2-scalars-in-app.ts`: `midpoint` is the overflow bug (A3).
- `wasm/3-calling-wasm.ts`: a stray `const c = a as Float16`.
- The tour, README and DESIGN still teach JS idioms where you chose `wrap`/`clamp`.
- `conversions.d.ts.part`: `clamp` truncates, where you chose rounding as `Uint8ClampedArray` does. "An instruction or two" is false for a double input (`wrap` is ToIntN, a helper). `Float32.clamp(Infinity)` contradicts its own doc.
- nts's `runtime/objc/objc.d.ts` says `NSInteger` is 64 bits and `CGFloat` a double "on every 64-bit Apple target". Both are false on watchOS arm64_32. That's outside the playground; I'm only noting it.

## E. Real-program friction (the JS developer)

- **Bigint sizes** are 5 of the 8 errors in the JS-developer program: `done / total * 100` with `size_t`, `ids.length` into a `size_t`, `strlen()` into `read()`'s count.
- **Typed-array reads are plain**, so `buf.put(data[i])` into a Java `byte` compiles, and nts would throw for every byte ≥ 0x80.
- **Error messages are poor.** Most were rated 1–2 out of 5: `'Float64' → 'c_int'` (for an integer!), `Scalar<"Int16"|"Uint16">`, and TS2352's advice to "convert to `unknown` first". None says why a value may not fit, or how to fix it.
- **The editor shows internals.** Completions list `__Uint8?`; hovers show no range; `c_char` appears in pure JS and wasm hovers; `Scalar<"A" | "B">` reads as "either" but means "both".
