# Memory and ownership

Ownership, reference counting, escape, liveness, lifetimes and frames.

Each line is a rule and the reason it exists. Add one when something costs you time that a rule would have saved; delete one when it stops being true.

- **When a callee-side ownership summary depends on how the function is called, list every way in (direct, virtual, closure, bridge, foreign runtime) and exclude any that does not honour it.** A function was allowed to take over a parameter it stores, but only direct calls hand a reference over, so the same object was freed early three times: called from UIKit, from an `enumerateObjects` block, and through a plain-TypeScript virtual call where the next allocation reused the freed memory.
- **C code that builds a value to pass to a compiled closure must release it after the call, because a closure borrows its arguments.** A closure that stores its parameter retains it itself and one that only reads it does neither, so `cares.c` and `net.c` leaked every value they built for a callback until this was fixed.
- **When tightening a conservative rule, run every reference-counting test arm before reasoning, and expect the failures to be other code's hidden reliance on the old slack.** Moving releases from block end to last use broke 12 checks, exposing a runtime sort helper that had double-released its array on every `xs.sort()`, a store that moved a reference while the local was still read, and a weak `assign` delegate that crashed when released early.
- **Before changing the ownership of a `runtime/c` accessor, grep `runtime/c/tests/` for its name, and fix the caller when a test asserts the callee's contract.** Making the promise payload readers retain made both sanitizer probes clean but failed a C test asserting "reading does not retain again", because the borrow contract lived only in that test, not in the header; a clean sanitizer run proves the counts balance, not that they balance the intended way.
- **Before marking a type cyclic, run the interop reference-counting captures (such as `gtk-values`), not just the examples' leak counts.** Marking `unknown[]` cyclic to fix a `xs.push(xs)` leak kept a `GtkButton` alive past its owner's death, because a cyclic object that reaches zero while buffered keeps its contents until the next collection, and GTK programs depend on prompt release.
- **For any flaky compiled result, build the artifact once and run it in a loop (`for i in $(seq 200) ...| sort | uniq -c`) before forming a hypothesis; varying values point at uninitialised memory.** A "read before its declaration ran" flake blamed on an unpinned binary was a frame-allocated cell whose `ready` flag was never written: 200 runs printed 200 different garbage numbers, and the JVM backend, which zero-initialises objects, gave the right answer.
- **Run any lowering that lends managed memory to C (strings, arrays, views) under reference counting too, repeating the calls and asserting the live-object count does not change, and make sure the lent value is used after the C call.** A `Uint8Array` lent to C passed every no-GC test and the gate, but under reference counting it was released before the C call (its last use was the length read) and the C code read freed memory, giving 15402 where 25302 is right.
- **When identical code gives a varying stop or answer, run it about 200 times, count every distinct output, and build the emitted C under MSan or Valgrind.** A "flaky" use-before-declaration abort was a stack-allocated cell left uninitialised: garbage usually passed the check and returned a random number (200 different wrong answers in 200 runs), and only the rare zero aborted.
- **Walk any new dataflow analysis in reverse postorder, never by block index, and run the `memory` gate step and the benches after changing block shapes.** Block numbers are allocation order, so the ownership pass treated forward edges of `if (a && b)` as back edges and dropped a pending take, raising counting operations from 18 to 38 with no test failing.
- **For an escape or lifetime bug, reduce to two calls in a row that read the first result, and check every op that carries the same pointer (Erase, Unerase, Convert, block parameters, forwarded and returned parameters).** Escape analysis lost track of identity through `Unerase`/`Convert` and through a parameter that was only forwarded, so GTK dialogs stack-allocated an object that a kept click handler later read, and crashed under `--rc`.
- **For a leaked root or live-count failure, first identify the leaked object and print a stack for each of its retains and releases, then reduce.** A DOM fuzz left one root that no fuzz operation could create (HTMLDocument); its extra retain came from a compiler reference-counting defect after a loop, which bisecting the fuzz operations would have blamed on the fuzz.
- **Get the shipping (elided) reference-counting build with `env -u NTS_RC_NAIVE`, never `NTS_RC_NAIVE=0`, and take recorded numbers from `tooling/memory/run.sh`.** The compiler checks only whether the variable is present, so a before/after written with `=0` measured the naive build twice and reported that elided and naive "agree exactly" when the elided build had 8 operations, not 11.
- **To make a value outlive its last read, add it to the anchors that feed `hold_to_every_exit` in `own::analyze`, never to `liveness::analyze`'s `used` set.** Inflating liveness fixed the target but silently moved three retains in `macos-classes`, because ownership is classified from liveness before the anchor stretch runs.
- **To test a reference-counting fix, force a cycle collection (or print the object header's count in the emitted C) and run under `NTS_RC=1 NTS_POISON=1 nts check`; for a crash in the collector, instrument the visit to name the parent and slot of a dangling child.** An extra release of a managed object is invisible to valgrind and to an immediate read, because buffered candidates are destroyed only at the next collection and the runtime pools its frees; GTK's real `g_object_unref` was what exposed one.
